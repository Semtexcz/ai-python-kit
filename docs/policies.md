# Engineering policies

This reference defines the project policy values and the checks and review associated with them. Presets and file ownership are specified in the [MVP architecture](mvp.md).

## Architecture and component contracts

Set `[architecture].style` to `modular`, `layered`, `hexagonal`, or `custom`. Describe the chosen boundaries and rationale in a project-owned file named by `[architecture].reference`. Configure root package and contracts in `.ai-python/config/importlinter.ini`. Set `[architecture].graph` to `contracts` or `flat`. A modular package with no intended internal boundary and at most one immediate importable production child (excluding `__init__.py`) can use `flat` with a reason recorded in the reference. Other layouts require contracts. Use `layers`, `forbidden`, `independence`, `protected`, and `acyclic_siblings` as appropriate. Enforce at least one meaningful contract in contract mode. Use `acyclic_siblings` for applicable package containers and preserve explicit direction in existing projects by mapping their actual modules. Include negative transitive cases where the selected contract promises indirect detection. [Import Linter contract reference](https://import-linter.readthedocs.io/en/stable/).

| Style | Passing example | Failing example |
| --- | --- | --- |
| Modular | `reports` imports the public `measurement` API. Its independent sibling remains independent. | `measurement` imports `reports` and closes a sibling cycle. |
| Layered | `presentation → application → domain`. Layers match the actual package layout. | `domain → presentation` or a re-export that creates the same forbidden edge. |
| Hexagonal | `adapters.sql → ports`. The composition root wires adapters into application code. | A domain function imports `adapters.sql` directly or through an internal helper. |
| Custom | A documented forbidden contract lets `factory` construct `drivers` while keeping `models` independent of them. | `models → drivers` crosses the project's explicit boundary. |

Prefer cohesive components with one responsibility, narrow public interfaces, internal encapsulation, low coupling, and visible direction. Keep computations separate from I/O and dependencies injectable at meaningful boundaries. Favor composition where it keeps behavior simpler, reuse real shared functionality, and introduce abstractions when the current change needs them. Review runtime imports, callbacks, and configuration-based coupling alongside the static graph.

State valid ranges and units, preconditions, postconditions, invariants, errors and side effects where relevant. Use types for representable constraints, validate untrusted and boundary inputs with explicit errors, and verify observable behavior with tests. For example, a converter accepting positive finite absolute temperatures documents the unit, rejects invalid inputs with a meaningful error, and tests a known conversion and invalid values. Enforce runtime validation with explicit code and tests for that component. A standalone Design by Contract framework is unnecessary.

## Dependencies

Set independent `[dependencies].runtime` and `.development` modes along with booleans `approve_runtime_additions` and `approve_development_additions`. Defaults are true for runtime and false for development. All dependency and lock diffs still receive ordinary review.

| Mode | Decision rule |
| --- | --- |
| `reuse-first` | Prefer mature maintained libraries when reuse improves quality or lowers maintenance cost. |
| `balanced` | Decide case by case. Document material tradeoffs. |
| `minimal` | Start with existing functions and the standard library. Require a concrete benefit for a third-party dependency. |
| `stdlib-only` | Reject direct declarations in the scope except exact approved package-name exceptions. All transitive dependencies introduced by exceptions need review. |

Runtime scope includes required and optional published dependencies, regardless of platform markers or current extra selection. Development scope covers all project-owned dependency groups, including unused groups, legacy `tool.uv.dev-dependencies` where present, and group inclusion targets. Build requirements have a distinct scope and receive review. The reserved `ai-python-kit` group contains the exact release tool set and carries no application dependencies. Project groups may not include the reserved group or its inverse. If project rules prohibit even isolated verification tooling, the full v0.1.0 gate set cannot be adopted. Report the incompatible requirement before promotion.

Check declarations using the [packaging requirement parser](https://packaging.pypa.io/en/stable/requirements.html) and normalized distribution names. Check supported static metadata, all direct declarations, named group references, and the reserved group inventory. Reject dynamic dependency metadata and invalid/unresolved group includes. Evaluate runtime uses with deptry on production paths (missing, unused, transitive and dev-only diagnostics). Do not count the kit and tests as runtime usage. Set deptry package/module mappings and individual native exceptions when review identifies false positives. Extras can need explicit usage evidence under the declared verification environment. Dynamic imports, plugins, dependencies used via subprocess, and tool-only development dependencies require review. [deptry diagnostics](https://deptry.com/rules-violations/).

In dependency review, check current project functionality, standard-library fit, maturity, maintenance, license, security, transitive resolution, portability, performance, API stability, and total maintenance cost. Explain the chosen scope, new or changed lock entries, and capability conflicts. Prefer vetted cryptographic and security libraries and mature implementations of complex algorithms. Report a policy conflict and ask for a scoped decision if a dependency is needed.

## Typing

The authoritative mypy config selects checked modules and strictness. Set `no_implicit_optional`, `warn_unused_ignores`, and `warn_redundant_casts` at all levels. Check bodies of untyped definitions. Standard uses `disallow_untyped_defs` on production modules. Strict uses mypy's pinned strict preset plus `disallow_any_explicit`. Projects may select explicit options such as `disallow_untyped_defs`, `disallow_incomplete_defs`, `disallow_any_generics`, `disallow_any_expr`, or module overrides. Use `[typing].annotation_scope` for API intent (`public`, `production`, `custom`) and a project-owned `scope_reference` when custom. Native module enforcement and semantic review cover public-only or per-object distinctions where mypy's options enforce a broader or narrower scope. In validation report the actual checked scope and verify that production paths are covered or have an approved deviation. Ruff's `PGH003` requires specific ignore codes. Review `Any`, a cast, or a type ignore for a demonstrated boundary and narrow it with real types or validation where possible. [mypy options](https://mypy.readthedocs.io/en/stable/config_file.html). [Python typing specification](https://typing.python.org/).

## Docstrings

Set `[docstrings].format` to `google`, `numpy`, `sphinx`, or `pep257`. PEP 257 defines conventions for summary and layout and can be used without a structured field syntax. Google, NumPy, and Sphinx select structured syntax. Set `scope` to `public`, `all`, or `custom`. Set `public_detail` and `private_detail` independently to `summary`, `standard`, or `detailed`. Set `language` to the project language, default `en`.

- Public covers public production modules, classes, functions, methods, and properties. A literal top-level `__all__` identifies public module declarations when present. Otherwise use non-underscore names and public enclosing objects. Report dynamic or ambiguous exports for review.
- All covers public and private production declarations, including explicit special methods. Test files are opt-in. Custom uses a nonempty `categories` array from `modules`, `classes`, `functions`, `methods`, `properties`, and `tests`. Selected categories include both public and private declarations. The `tests` category covers test modules, test classes and test functions/methods in configured test roots. Test fixtures follow ordinary semantic review.
- The presence gate inspects module-level definitions and class bodies with a narrow Python AST adapter, including async variants. Recognize literal property decorators `property`, `cached_property`, and accessor decorators, count an accessor as documented through its property's getter, and normalize overloads to their concrete definition when present. Nested helper functions, generated declarations, dynamically attached methods, and inherited docs need review where relevant. Require a nonempty docstring for matching objects and reject empty or omitted scope. Ruff checks common formatting rules such as D205, D209, D210, and D300, with additional convention-compatible rules owned by native config. Ruff public-presence rules inform the design. One presence gate covers the wider scopes.
- Run pydoclint as a required Flake8 plugin on regular Python files in the configured source roots and test roots when `tests` is selected, including in-progress source. Select only docstring diagnostics. Seed `DOC001`, `DOC002`, `DOC101`–`DOC104`, `DOC201`, `DOC202`, and `DOC402` in `.ai-python/config/flake8.ini`. Keep short-summary handling enabled. Omit diagnostics that mandate annotations or duplicated type hints so this gate composes with any typing level. For PEP 257-only projects, report the structured signature check as skipped by policy and review prose against the signature. The detail distinctions, natural language, completeness, inferred/generated declarations, and factual accuracy are semantic. [Diagnostic reference](https://jsh9.github.io/pydoclint/violation_codes.html).
- Summary states purpose or observable behavior. Standard adds applicable parameters, returns, exceptions and relevant side effects. Detailed also covers applicable pre/postconditions, invariants, units, assumptions, limitations, and examples. Use only applicable material. Update the docstring in the same change as the behavior or signature. For example, a documented argument `distance_m` in a signature accepting `distance_km` fails consistency for supported structured formats. A structurally valid docstring that states the wrong units fails review.

Sources include [PEP 257](https://peps.python.org/pep-0257/), [Google style](https://google.github.io/styleguide/pyguide.html#38-comments-and-docstrings), [NumPy conventions](https://numpydoc.readthedocs.io/en/latest/format.html), [Sphinx fields](https://www.sphinx-doc.org/en/master/usage/domains/python.html#info-field-lists), and [pydoclint options](https://jsh9.github.io/pydoclint/config_options.html).

## Testing

The pytest config declares markers, enables strict marker checking and strict expected failure, and uses importlib import mode for new projects. The command passes test roots from `[project].tests`. Configure `[testing].categories` as a nonempty list drawn from `unit`, `integration`, `regression`, `property`, and `end_to_end`. Defaults include unit and regression. Unmarked tests count as unit. Build the native pytest `-m` expression as the union of selected category marks. When unit is selected, also include tests without any category mark. Qualify tests that depend on live infrastructure, specialized stochastic methods, or performance with the distinct `external`, `stochastic`, or `performance` marker. Subtract these three marks from the resulting selector. Document explicit commands and environment for separate runs. Verify that a default suite executes at least one test. Empty selection fails.

The default command explicitly loads pytest-socket, denies Python socket creation, and enables no network allowlists. The plugin establishes test-process isolation for Python sockets. Native libraries, subprocesses, and plugin opt-outs are outside that guarantee. Review test markers, fixtures and environment for socket exceptions. Run specialized external tests with explicit authorization and separate evidence. Use temporary directories and scoped environment patches. Restore mutable globals, seed random sources, inject clocks or use narrowly scoped clock fixtures, isolate database state with disposable resources/transactions, and use synchronization primitives with failure-bound timeouts. Never cover flakes with reruns. Triangulate meaningful behavior using normal, boundary, and rejected cases and independent expected results. A defect correction needs a regression case that would fail before the fix.

Use coverage.py native config in `.ai-python/config/coverage.ini` for line/branch mode, source/include/exclude, and the effective `fail_under`. Clear old measurements and report after each successful deterministic run. Review meaningful uncovered branches and threshold changes. A test suite can be reproducible with a fixed seed, toolchain and input record even when sampled data or scheduling differs in another environment. Default tests must give stable assertions and outcomes under their controlled inputs. Record seeds, dependencies and environment for optional property-based tools such as Hypothesis. [pytest documentation](https://docs.pytest.org/). [pytest-socket](https://github.com/miketheman/pytest-socket). [coverage.py configuration](https://coverage.readthedocs.io/en/latest/config.html).

## Maintainability and security

Use Ruff native config for lint/format, dead local code indicators (`F401`, `F841`), cyclomatic complexity (`C901`), and optionally `PLR0912` branches, `PLR0915` statements, and `PLR0913` arguments. Function and module line counts, dead public code, redundant implementations, and premature abstractions are advisory. Give teams optional `[review]` positive integer fields `function_lines` (default 60) and `module_lines` (default 400) as review triggers. Review the reason for complexity and favor cohesive code. Avoid splitting a function merely to satisfy a threshold. [Ruff rule index](https://docs.astral.sh/ruff/rules/).

Select Ruff security rules `S102`, `S105`–`S107`, and `S307` as initial controls for risky constructs and hardcoded credentials. Use Gitleaks and the online dependency check specified in [Verification](verification.md). Review input validation, configuration and secret boundaries, justified constants, explicit errors and logging without sensitive data, and the intended public interface. These controls provide signals about specific risks. Security assurance includes review and upstream data freshness.

## Scientific computing

Use explicit physical units at interfaces, in fixtures, and in docstrings. Check dimensional consistency and specify assumptions, validity limits, boundary conditions, and conservation properties where applicable. Prefer stable formulations. Explain floating-point roundoff and choose justified absolute and relative tolerances by scale, units, and conditioning. For example, test a conserved total against an independently calculated expected value and a justified tolerance. A tolerance copied from a current output can hide drift.

Use analytic solutions or independent reference data where available, published provenance for test inputs, and convergence tests for numerical approximations. Record toolchain, algorithm settings, thread counts, seeds, and platform assumptions when results depend on them. Use a project-approved scientific library when warranted. Profile selection adds no required runtime dependency. [Scientific Python Development Guide](https://learn.scientific-python.org/development/).
