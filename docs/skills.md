# Agent Skills and project guardrails

The kit uses the open [Agent Skills specification](https://agentskills.io/specification) and the [AGENTS.md convention](https://agents.md/). Skills are planned M2 deliverables.

## Discovery and precedence

The canonical copy lives in `.ai-python/kit/skills/<name>/SKILL.md`. Each folder and frontmatter name match. Write a short description with triggering tasks. Keep workflow text in the entry and task-specific examples or sources in `references/`. Default to documentation-only skills. The maintainer acceptance suite validates structure with the pinned upstream `skills-ref validate` command, outside the consumer tool group. Validation covers the metadata shape. Content, licensing and trust need review. [Reference validator](https://github.com/agentskills/agentskills/tree/main/skills-ref). [Skill authoring guidance](https://learn.chatgpt.com/docs/build-skills).

Generated root `AGENTS.md` identifies the authority, workflow entry point and mandatory guardrails. Adoption adds a reviewed routing block without removing existing instructions. Configure the host to search the canonical location when supported. For hosts that use a project discovery directory such as `.agents/skills`, opt in by linking individual directories where the host and platform support links. Never claim a discovered name without checking for collisions. If native discovery or links are unavailable, read the appropriate `SKILL.md` directly and follow the linked references. Avoid duplicate copies.

Authority flows from authorized project instructions and current adopted policy to the kit's workflow instructions, then to reviewed upstream recommendations. Raise incompatible project rules before acting. Mandatory gates and review requirements apply regardless of skill activation. Reuse the [engineering policies](policies.md) and [verification contract](verification.md) via links.

## Kit workflows

| Skill | Trigger and result |
| --- | --- |
| `python-implement` | Start an authorized change. Inspect policy, similar code and relevant contracts. Make a small change with meaningful tests and docstring updates. Invoke verification and provide evidence. |
| `python-review` | Review a concrete diff independently of its author. Inspect code, tests and tool output and report evidence and actionable findings before disposition. |
| `python-audit` | Review project-level engineering risks, scope, and approved exceptions against actual code and evidence. Reuse the same evidence and findings format as review. |
| `python-verify` | Run the applicable unified check, report outcomes, and preserve pending evidence for skipped and unexecuted work. |
| `python-architecture` | Select or assess proportionate boundaries, direction and component contracts. Prove static constraints with positive and negative fixtures. |
| `python-dependencies` | Compare reuse options, evaluate compatibility and approve-through-maintainer workflow, and review manifest and lock changes. |

Keep six small entries for distinct triggers. Share one review checklist for review and audit and one evidence reference for implementation and verification. Route architecture and dependencies only when relevant. Load scientific or asynchronous guidance in context. Upstream skills supplement these entries and do not replace them.

## Mandatory guardrails

Generated instructions require agents to inspect existing functionality, keep the change within authorized scope and follow architecture contracts. They prohibit weakening tests or gates to pass, broad suppressions, bypasses using `Any`, casts or ignores, suppressed failures, redundant implementations, speculative abstractions, unauthorized dependencies, and scope expansion. They also prohibit filler docstrings, test oracles derived from the implementation, low-value coverage inflation, flaky substitutes, and passing or completion claims without execution evidence. Cite affected behavior, policy and verification results when reporting completion.

Tool configurations and deterministic fixtures catch selected rule violations. Semantic review examines intent, workarounds, test quality, suppression scope and evidence. Repository controls enforce maintainer review for policy changes. An agent's description of its permissions or successful checks does not establish authority.

## Approvals and exceptions

Keep the exception ledger in project-owned `.ai-python/policy.toml` as `[[exceptions]]` records. Require stable unique nonempty string `id`, exact `rule`, narrow `target` (specific path/object, import pair, dependency name, or baseline threshold), `reason`, accountable `owner`, `approved_by`, date `approved_on`, UTC date `expires_on` (effective through that date), and `approval_ref` pointing to the human decision that identifies the approved scope. Local and CI use current UTC for acceptance and record the date. Test fixtures can freeze the date for repeatable boundary cases. An expired record fails the applicable gate before allowing a violation. An unapproved proposal stays in the change discussion and confers no permission.

For `stdlib-only`, use exact normalized package names, with `rule = "dependency.runtime"` or `"dependency.development"`. Native exceptions use exact rule codes and paths, objects, or import edges. Tool flags and narrow native suppressions apply the exceptions. Records point to the implementing suppression where needed. Maintainers review mappings where tool output has no stable identity. Review dependency additions and lock diffs even when no exception is used. When a policy requires prior approval, capture a scoped human decision before introducing the dependency.

Protect the default branch and require passing CI, a human maintainer review of changes to policy, tool configs, gates, workflows, skills, suppressions and dependency files, and a fresh approval after relevant changes. On GitHub use required checks and owner review with stale reviews dismissed as supported by the repository's rules. For local-only projects the maintainer reviews and accepts the exact change from a separate trusted action. In a permitted repository with no protection, the acceptance report explicitly states that approval is manual. Structural validation verifies scope, dates and references. It cannot authenticate a reviewer or prove that the decision covers the final content. [GitHub rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets).
